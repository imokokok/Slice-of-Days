# 第四阶段：第一天与核心居民开发层

## 本阶段目标

把“能从地图触发事件”的第一天升级成可直接试玩的开场，同时让十二名核心居民从日程名字变成可以持续写作的人物。此阶段仍使用占位对白和概念美术，不锁死正式角色设计。

## 第一天新手叙事链

### A：让路线被一次相遇改变

1. 在地图标记打印店并选择交通方式。
2. 在打印店逐拍经历U盘事件，选择借出手机或陪对方使用店内电脑。
3. 线索把A带到咖啡馆；Mossner发出剧场邀约，系统生成可追踪预约。
4. A在彩排结束后和Mossner、剧场道具师共同收尾，获得两份有具体经历依据的认可。
5. 傍晚去公园进入摄影工作台；第一天以私人照片和短暂异常结束。

### B：准确记录，也记录边界

1. 前往学院食堂确认周晓六的出现时间。
2. 选择记录准确位置，或记录“点头不等于有空”；两者都保留可靠日程，但形成不同的关系记忆。
3. 在18:00前后去图书馆看见九。正确抵达不会自动换来对话或认可。
4. 回到住处整理计划本，旧门牌异常只写入B的私人记录。

主界面底部的“当前引导”会根据角色与已完成事件更新，只说明下一步可做什么，不隐藏时间成本或替玩家决定选择。

## 十二名核心居民

`data/npcs/core_residents.json` 为以下稳定居民 ID 提供人物层：夏透明、Mossner、周晓六、九、Sunniva、阿锰、石泳琪、巫巫、见沼香、饭店店主、剧场道具师、代写委托人。

每人都有公开面貌、私人压力、认可依据、拒绝依据、说话方式、A/B 视角差异、视觉母题与两组环境闲聊。它们目前承担三项作用：

- 在计划本的关系栏中解释“这个人是谁、当前主角会被怎样看待”。
- 让公共地点的短交流不再统一使用模板句。
- 给后续专属事件、拒绝/修复场景和人物美术提供一致的写作边界。

`ResidentProfileSystem` 只负责读取与查询人物资料，不管理认可结果。认可仍由 `RelationshipSystem` 和剧情事件结算，因此修改人物措辞不会破坏已有存档。

## 新增占位美术

`art/locations/print_shop/print_shop_morning_v01.png` 是第一天打印店舞台背景。事件通过 `presentation.image_path` 引用它。正式版本可以直接覆盖同路径，或在事件数据中改成新路径。

## 后续替换边界

- 可以直接替换：所有 `presentation.beats` 正文、说话人显示名、舞台提示、人物资料文本、环境闲聊、图片和声音。
- 建议保持：居民 ID、事件 ID、选择 ID、预约 ID、玩法模块 ID 与结果字段。
- 如果正式设定改变某位居民的职业或拒绝理由，只需改人物表及相关场景文本；若改变实际认可条件，再同步修改对应事件 `results`。

## 下一步建议

1. 为第二天饭店工作台补一张场景背景，并把店主的认可写成一次看得见的共同劳动。
2. 为第三天声音采样补阿锰/声音师专属场景与授权选择。
3. 为第五天代写补委托人的删改对白，让工作台选句回到后续对话。
4. 为核心居民逐个增加“认可、拒绝、修复”三类事件，但先做已进入七天主路线的角色。
