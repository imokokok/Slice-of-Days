# 第二阶段游戏骨架

## 目标

这一阶段把第一天原型升级为可持续录入七天内容的工程结构。剧情对白、最终数值和玩法细节仍可替换，但角色状态、章节、事件、关系、时间、路线和存档已经有稳定入口。

## 核心系统

### 双视角状态

GameState 同时保存 A 和 B 的独立状态。每条线路分别记录日期、时间、金钱、地点、事件、关键选择、居民关系、认可、已知事实、日记、作品、预约和已知日程。switch_to_role 会先提交当前线路，再载入另一条线路。

共享状态只保存章节进度、过场完成情况和明确标记为公共的作品。A 与 B 默认不会继承彼此的私人信息。

`data/story/characters.json` 把 A/B 的职业、背景、野心、内在矛盾、生活习惯、美术方向与记忆意象独立保存。CharacterSystem 向界面提供人物资料；正式名字、立绘和设定细化时无需改动事件或存档结构。

### 七天章节

ChapterSystem 根据 calendar.json 生成十四个角色章节。新游戏所选角色决定每天先体验哪一位，完成一个角色章节后进入章节过场，再切换到下一个角色章节。

`data/story/day_openings.json` 为十四个角色章节分别提供开场卡，保存当日主题、角色重点和内在线索。每张开场只在对应章节首次进入时出现，已读状态进入共享存档。

### 时间安排

calendar.json 保存角色的默认时间块和逐日覆盖。A 默认使用连续时间，B 默认使用多个碎片时间。正式排期确定后只需修改数据，不必改动状态系统。

### 剧情事件

EventSystem 从 events.json 读取事件。事件支持：

- 角色、日期、地点、时间和在场居民条件。
- 前置事件、排除事件和已知事实条件。
- 时间与金钱成本。
- 新事实、相遇、关系记忆、认可状态、日记、作品、预约和日程情报结果。

小镇界面会自动显示当前条件允许、且当前资源能够支付的事件。

计划本的“今日可追踪机会”会忽略玩家当前所在位置，但仍检查角色、日期、前置事件、事实和预约条件，因此它是路线提示而不是无条件剧透。已过时间窗的机会仍会显示为错过，方便理解路线失败原因。

### 居民关系与认可

RelationshipSystem 不使用公开好感度。每位居民记录相遇次数、具体经历标记、最后一次事件和认可状态。认可状态包括未知、待定、同意、拒绝和撤回。

标记为 `draft` 的居民使用一套可扩展的认可请求流程：一次相处后立刻请求会被拒绝，两次相处后进入待定，三次相处后可以认可；曾经拒绝的居民在积累四次真实相遇后允许修复。正式主要角色仍由专属剧情事件控制，不套用这条通用规则。

### 地图与交通

TravelSystem 从 travel_routes.json 读取地点之间的步行连接，并计算最短路线。公交、出租车和朋友顺路在步行距离上换算时间与费用。新增地点不再依赖代码中的数组顺序。

主地图保留高频地点，唱片店、旧车站、港口、摄影棚和手作店通过底部“街区里的地点”进入，避免在一张插画上堆叠过多按钮。这五处已经接入居民日程、路线和可选事件，不再是仅存在于数据里的隐藏节点。

### 预约与错过

预约拥有待赴约、当前可赴约、已完成和已错过四种状态。当前时间进入窗口后预约激活；完成同 ID 事件后自动结算；跨过截止时间则生成一次错过记录，消耗的时间不会退回。地图会标出今天有预约的地点，计划本同时显示时间窗、地点和状态。

### 章节过场

chapter_transition.tscn 提供可运行的平行记录轻交互。`data/story/transitions.json` 按七天分别保存“同一天换视角”和“进入下一天”两类片段，画面会在照片、计划页、手绘地图、声音波形、棋局和晚霞之间变化，但不会显示数值。完成对齐后，系统提交当前角色状态、推进章节、切换视角并自动保存。

每张 A/B 记录都支持可选的 `image_path`。未提供正式美术时使用当前暖色小镇背景和角色色洗；正式拍立得、手绘地图或本子页面到位后，只需填写资源路径即可逐张替换，不需要修改章节逻辑。

### 存档

存档格式版本为 3，同时保存两位角色、关键选择和共享章节状态。三个存档位使用独立文件，原有 `solmere_save.json` 保持为存档 1；旧的第一阶段单角色存档会在读取时迁移。

主菜单另有独立设置文件，保存全屏、主音量和减少章节转场位移，不与某一条旅程绑定。

### 结局

`data/story/endings.json` 保存双通过、仅 A 通过、仅 B 通过和均未通过四类审核结果，以及关键日记、错过预约和公共作品的回声。结局只陈述已经发生的结果，不替角色做作者式总结；正式结局插画可通过分支的 `image_path` 单独替换。

### 玩法模块

GameplayModuleSystem 读取 modules.json，按角色记录玩法解锁、进入次数、是否完成和每次结果。剧情事件可以通过 unlock_modules 解锁玩法，独立玩法场景完成后把结果写回当前角色状态。

目前已经提供烹饪选材、代写拼句、误解补全、声音排序、棋局观察、发呆取景、摄影构图和空间记录选择工作台。玩家在决定结算方式前需要完成对应桌面操作，所选材料、句子、声音或记录会随玩法结果保存。塔罗保留独立牌桌，并增加“确认两条有效事实后换取免费占卜”的完成闭环。空间错觉只验证选择与结果接口，不锁定最终2D、2.5D或3D表现。

尚未拥有专属剧情的在场居民也支持每天一次短交流。短交流消耗时间并留下具体关系记忆，但不会直接给出认可。当前名单已扩展为 32 位显式居民与 68 位模板化灰盒居民，共 100 个稳定 ID；高人流地点只在地图侧栏展示前三个名字和总人数，避免界面溢出。

## 内容文件

- data/story/calendar.json：七天时间和章节基础配置。
- data/story/characters.json：A/B 人物骨架、视觉方向与记忆意象。
- data/story/day_openings.json：十四段每日角色开场。
- data/story/events.json：数据驱动剧情事件。
- data/story/transitions.json：七天 A/B 平行记录与章节轻交互文本。
- data/story/endings.json：四类审核结局和选择回声。
- data/npcs/demo_npcs.json：32 位显式居民、68 位生成居民名称、日程模板与最终 100 人名单。
- data/world/locations.json：地点展示与地图可见性。
- data/world/travel_routes.json：地点连通关系。
- data/gameplay/modules.json：玩法模块登记。
- data/gameplay/module_prototypes.json：灰盒玩法选择、成本与结果。
- docs/ART_REPLACEMENT_GUIDE.md：正式美术接入路径与建议规格。

## 继续填充内容时的顺序

1. 用正式对白替换灰盒事件中的 summary、lines 和 result。
2. 用正式人物设定替换标记为 draft 的居民展示名与日程。
3. 接入正式立绘、地点背景、道具、声音和动画；主角先填写 `characters.json` 的资源路径。
4. 由对应制作人员深化 8 个玩法工作台，同时保留现有成本与结果接口。
5. 调整数值后持续运行七天可完成性模拟。

## 验证

运行三个 Godot 无头测试场景：

- scenes/system_smoke_test.tscn：双视角隔离、日历、路线、事件、关系、玩法状态、章节和存档。
- scenes/content_validation_test.tscn：地点、NPC、日程、事件、玩法ID和结果引用。
- scenes/seven_day_simulation_test.tscn：A与B各自从第1天走到至少12份认可的可完成路线。
