# 第二阶段游戏骨架

## 目标

这一阶段把第一天原型升级为可持续录入七天内容的工程结构。剧情对白、最终数值和玩法细节仍可替换，但角色状态、章节、事件、关系、时间、路线和存档已经有稳定入口。

## 核心系统

### 双视角状态

GameState 同时保存 A 和 B 的独立状态。每条线路分别记录日期、时间、金钱、地点、事件、居民关系、认可、已知事实、日记、作品、预约和已知日程。switch_to_role 会先提交当前线路，再载入另一条线路。

共享状态只保存章节进度、过场完成情况和明确标记为公共的作品。A 与 B 默认不会继承彼此的私人信息。

### 七天章节

ChapterSystem 根据 calendar.json 生成十四个角色章节。新游戏所选角色决定每天先体验哪一位，完成一个角色章节后进入章节过场，再切换到下一个角色章节。

### 时间安排

calendar.json 保存角色的默认时间块和逐日覆盖。A 默认使用连续时间，B 默认使用多个碎片时间。正式排期确定后只需修改数据，不必改动状态系统。

### 剧情事件

EventSystem 从 events.json 读取事件。事件支持：

- 角色、日期、地点、时间和在场居民条件。
- 前置事件、排除事件和已知事实条件。
- 时间与金钱成本。
- 新事实、相遇、关系记忆、认可状态、日记、作品、预约和日程情报结果。

小镇界面会自动显示当前条件允许、且当前资源能够支付的事件。

### 居民关系与认可

RelationshipSystem 不使用公开好感度。每位居民记录相遇次数、具体经历标记、最后一次事件和认可状态。认可状态包括未知、待定、同意、拒绝和撤回。

### 地图与交通

TravelSystem 从 travel_routes.json 读取地点之间的步行连接，并计算最短路线。公交、出租车和朋友顺路在步行距离上换算时间与费用。新增地点不再依赖代码中的数组顺序。

### 章节过场

chapter_transition.tscn 提供可运行的照片对齐过场骨架。完成对齐后，系统提交当前角色状态、推进章节、切换视角并自动保存。

### 存档

存档格式版本为 2，同时保存两位角色和共享章节状态。旧的第一阶段单角色存档会在读取时迁移，并写入新的 solmere_save.json。

### 玩法模块

GameplayModuleSystem 读取 modules.json，按角色记录玩法解锁、进入次数、是否完成和每次结果。剧情事件可以通过 unlock_modules 解锁玩法，独立玩法场景完成后把结果写回当前角色状态。

目前已经提供烹饪、代写、误解翻译、声音采样、棋局、发呆、摄影和空间错觉的通用灰盒工作台。塔罗保留独立牌桌，并增加“确认两条有效事实后换取免费占卜”的完成闭环。空间错觉只验证选择与结果接口，不锁定最终2D、2.5D或3D表现。

## 内容文件

- data/story/calendar.json：七天时间和章节基础配置。
- data/story/events.json：数据驱动剧情事件。
- data/npcs/demo_npcs.json：居民与七日日程。
- data/world/locations.json：地点展示与地图可见性。
- data/world/travel_routes.json：地点连通关系。
- data/gameplay/modules.json：玩法模块登记。
- data/gameplay/module_prototypes.json：灰盒玩法选择、成本与结果。

## 继续填充内容时的顺序

1. 用正式对白替换灰盒事件中的 summary、lines 和 result。
2. 用正式人物设定替换标记为 draft 的居民展示名与日程。
3. 为各玩法逐个替换通用工作台，保留现有成本与结果接口。
4. 接入正式立绘、地点背景、道具、声音和动画。
5. 调整数值后持续运行七天可完成性模拟。

## 验证

运行三个 Godot 无头测试场景：

- scenes/system_smoke_test.tscn：双视角隔离、日历、路线、事件、关系、玩法状态、章节和存档。
- scenes/content_validation_test.tscn：地点、NPC、日程、事件、玩法ID和结果引用。
- scenes/seven_day_simulation_test.tscn：A与B各自从第1天走到至少12份认可的可完成路线。
