# 把项目交给合作者

这份工程是 Godot 2D 正面料理台小游戏原型，带独立运行的宿主示例。给程序合作者发送**完整源码工程包**，给只试玩的人发送 Windows 试玩包。程序合作者拿到 exe 不能继续编辑场景、脚本或数据。

## 现在需要发什么

1. 完整源码：`project.godot`、`demo_host.gd/.tscn`、`icon.svg`、`modules/restaurant/`、`docs/`，以及仓库中的配置、测试、导出预设。
2. 请对方先读 `README.md` 和 `docs/INTEGRATION.md`，再用 **Godot 4.7.2 Standard / GDScript** 导入 `project.godot`，按 F6/F5 运行对应场景/项目。
3. 如果对方只需要接进已有 Godot 工程，完整复制 `modules/restaurant/`，另附集成文档；其中字体、数据、场景、脚本、UID 都必须保留。无需复制演示宿主，也无需新增 Autoload 或替换对方主场景。
4. 试玩包可另附，方便不装编辑器的人检查体验；它不能替代源码。

所有 `.gd` 旁的 `.gd.uid` 应跟随提交；`.tscn`、`.tres`、原始资产与资产旁的 `.import` 设置也应保留。`.godot/` 是可重建导入缓存，不要打包或提交。排除导出目录、临时测试存档、个人账号文件和私人聊天截图。引用图中的讨论只作为策划来源，不作为需要向协作者传播的素材。

## 推荐分工边界

| 部分 | 主要文件 | 负责人适合处理的工作 |
| --- | --- | --- |
| 玩法与结算 | `domain/kitchen_session.gd` | 食材状态、料理评价、班次结算、顾客规则 |
| 关卡与交互 | `world/kitchen_world.gd` | 鼠标拖拽、刀刃切割、挤酱、2D 食材物理和交互反馈 |
| 厨房美术 | `world/kitchen_backdrop.gd`、`world/kitchen_foreground.gd` | 日间暖色、硬边几何、与交互区域一致的工作台表现 |
| 界面与绘画 | `ui/`，尤其 `poster_canvas.gd` | 菜谱和海报的空白纸面、图层编辑、照片裁剪、顾客信息与中文排版 |
| 本地数据 | `storage/` | JSON 版本、导入导出、错误恢复 |
| 内容设计 | `data/ingredients.json`、`data/customers.json` | 食材、NPC 偏好、价格和节奏 |
| 主游戏接入 | `restaurant` 根场景 + 宿主 | 钱包、玩家身份、NPC 日程、场景路由 |

这些是减少冲突的文件边界，不是必须由六个人负责。两人合作时可以一人管玩法与接入，一人管世界、界面与内容。开始改根场景前在协作渠道约定一下，避免同时重做同一文件。

## 本轮交接重点

厨房已改为日间暖色调，继续沿用简化硬边几何；环境图不要包含可拖动的刀或食材。刀具按住拖动、松手放下，回收命中区域与图形位置要一起验收，尤其检查在界面面板上松手的情况。

菜谱和海报从空白纸面开始，素材在纸外；玩家选择后加入食材、文字、照片或装饰图层。图层的拖移、旋转、缩放、前后顺序和多边形裁剪由 `PosterCanvas` 管理，根界面只负责提供工具入口。程序与美术修改时保留稳定食材 ID、图形原点和归一化布局，避免旧作品的食材图形或剪裁位置发生意外偏移。

一份菜谱的纸面布局随菜谱 JSON 的 `poster` 字段保存；内嵌照片随文件一起交换。发送源码给合作者与发送玩家作品是两件独立操作：合作者开发用源码工程；作品共享用本地 JSON 导出文件。当前没有云端公共图库、自动同步或多人同时编辑。正式主项目继续由宿主管理钱包、NPC 日程、进入/退出路由；模块只发出事件，不自行切换全局场景。

## Git 协作约定

- 两人使用相同 Godot 小版本；升级编辑器单独开分支，重新执行测试和打开场景。
- 一个功能一个分支，例如 `feature/customer-dialogue`；提交说明交代玩家可见行为与验证结果。
- 合并前先同步主分支，并完成一次源码导入、运行、结算、重进小游戏的检查。
- 尽量在独立子场景或脚本中做功能；避免两个人同时编辑根 `.tscn`。
- 不修改稳定食材/NPC ID 来“改名”。改显示名即可；删改 ID 需要兼容旧菜谱及存档。
- JSON 格式变更需要增加 `schema_version` 并实现迁移。先让旧格式可读，再切换写入格式。
- 不把本地用户目录的路径硬编码进脚本；程序资源用 `res://`，玩家数据用 `user://`。

## 合并前验收

先通过根 README 中的测试命令，再进行一次实际试玩：选择食材、加工、装盘、与顾客互动、上菜、结束班次；确认宿主只收一次 30% 分成。创建署名菜谱与海报，在空白纸上加入食材、文字和照片，至少测试一次旋转、缩放、层序与多边形裁剪。退出重进，再把导出的 JSON 导入第二份存档，检查布局、裁剪、照片、做法和作者仍可读取。刀具回归另运行 `tests/test_knife_drag.gd`，覆盖真实按下、拖动及在 UI 上松手的输入路径。

不要把参考游戏的商业素材放进仓库。当前字体附带 `assets/fonts/OFL.txt`；以后新增模型、贴图、音效时记录来源与授权，并一并交付需要的授权文件。

## 原型与后续工作

当前主要目的是把烹饪、顾客评价、班次收入、菜谱留存和海报创作串成可运行流程。厨房采用日间暖色的 2D 正面料理台、可拖动食材与原创矢量图形，菜谱和海报提供自由纸面拼贴。物理切割有每份最多四块的范围；更精细的连续切割、液体体积模拟、实时多人联机和线上社区属于后续工作。

公共菜谱当前在本地保存，跨电脑靠 JSON 交换；排行榜中的喜欢也是本地记录。正式上线应单独安排账号、服务器持久化、图片存储、并发冲突、内容管理与服务端结算。NPC 的世界日程和永久关系属于主游戏，应通过接口接入，不能由小游戏另建一套相互冲突的权威数据。

本轮增加的独立协作文件：`world/pan_controller.gd`（移动锅、水槽）、`world/pan_art.gd` / `sink_faucet.gd`（图形）、`world/kitchen_audio.gd` / `assets/audio/`（音效）、`domain/customer_review.gd`（人物评价）。替换音效可保留文件名；更换画面时同步核对锅柄和龙头命中区。对应新回归已加入 `tools/test.ps1` 和 CI。
