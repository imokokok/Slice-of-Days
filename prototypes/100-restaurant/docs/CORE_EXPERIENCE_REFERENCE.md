# 饭店小游戏：核心参考与整体体验改造指令

请将本章节视为整个饭店小游戏后续设计和实现的**最高层体验与视觉指导**。它用于解释完整开发规格中各项功能最终应该呈现出的感觉。

不要机械复制任何参考游戏的具体素材、角色、UI、地图、菜谱、动画或代码。参考的是设计语言、交互原则、空间组织和体验质量，并结合当前项目形成原创实现。

---

# 01. 四个参考游戏的职责必须严格区分

本游戏的参考优先级如下：

## 第一主参考：Good Pizza, Great Pizza

《Good Pizza, Great Pizza》是目前最重要的整体体验与视觉参考。

主要参考：

- 温暖、舒服、有生活感的 2D 餐厅氛围；
- 简洁但完成度高的二维插画；
- 柔和、略带手绘感的几何造型；
- 食物清楚、可爱、有食欲；
- 顾客站在玩家面前直接交流；
- 顾客拥有明显不同的外形、性格和说话方式；
- 点单与人物聊天自然连接；
- UI 不抢画面；
- 经营系统存在，但不会让整个游戏看起来像廉价手机经营游戏；
- 日常、轻松、偶尔荒诞的幽默感；
- 顾客反复出现之后逐渐形成熟悉感；
- “经营一家小店”本身带来的生活感。

本项目最终打开时，第一视觉印象可以接近：

**Good Pizza, Great Pizza 式温暖精致的 2D 小店体验。**

但是不要复制它的披萨店布局。

本项目是一间拥有完整厨房、多个工作区域，并且允许玩家在其中移动的饭店。

不要把所有做饭行为压缩在一张固定操作桌上。

---

# 02. 厨房不是一个操作界面，而是真正存在的空间

这是本项目与 Good Pizza, Great Pizza 最大的区别之一。

玩家拥有一个**完整、连续、可以移动的二维厨房**。

可以参考 Overcooked 对厨房功能区域的组织思路，但不要复制其俯视多人闯关形式。

本项目仍然保持自己的 2D 插画视觉。

厨房至少需要自然形成以下功能区域：

### A. 顾客柜台 / 出餐窗口

顾客来到这里。

玩家可以：

- 看见顾客；
- 接受订单；
- 聊天；
- 查看顾客当前状态；
- 上菜；
- 得到反馈；
- 查看餐前和餐后心情变化。

这里承担类似 Good Pizza, Great Pizza 的面对面顾客互动。

---

### B. 食材储存区域

包括：

- 冰箱；
- 冷藏柜；
- 普通柜子；
- 开放式置物架；
- 食材篮；
- 调味料区域；
- 奇异材料区域。

玩家不能点击一个统一的“Inventory”按钮就凭空获得所有食材。

例如玩家需要洋葱：

走到储存区域 → 打开对应位置 → 找到洋葱 → 拿出来 → 带到备菜区域。

如果玩家想捣乱，则可以去奇异材料区域拿完全不应该进入料理的东西。

---

### C. 洗涤区域

包括：

- 水槽；
- 水龙头；
- 洗菜容器；
- 洗碗区域。

水应该属于厨房实际交互的一部分。

---

### D. 备菜区域

包括：

- 砧板；
- 刀具；
- 临时食材容器；
- 调味工具。

玩家把刚刚取得的食材带到这里。

进入切菜操作时，可以从厨房空间自然过渡到更近的操作视角。

不要把食材缩得很小。

此时食材应该占据足够大的画面面积，让玩家能够看清：

- 刀刃；
- 切口；
- 食材内部；
- 不同大小的切块；
- 表面状态；
- 已经附着的材料。

---

### E. 烹饪区域

包括：

- 炉灶；
- 锅；
- 平底锅；
- 锅铲；
- 勺子；
- 其他实际需要的器具。

玩家把处理好的食材带到这里。

锅不是“点击开始烹饪”的按钮。

锅本身是一个实际容器。

玩家将什么放进去，锅里就有什么。

---

### F. 装盘区域

包括：

- 不同盘子；
- 碗；
- 装饰材料；
- 酱汁；
- 摆盘空间。

这里应该进入比较大的近景。

玩家可以真正决定最后一道菜长什么样。

---

### G. 摄影 / DIY 菜谱工作台

这里属于本项目非常重要的特色区域。

玩家可以把自己实际做出来的菜：

拍照 → 命名 → 保存做法 → 制作菜谱 → 制作菜单 → 制作宣传材料。

照片必须来自刚才实际摆好的那一盘菜。

---

# 03. 玩家如何在二维厨房里移动

不要因为是 2D，就把厨房做成一排按钮。

玩家需要感觉自己真的处于一个空间里。

建议采用：

**2D 横向 / 轻微纵深的连续厨房空间。**

人物可以在厨房中移动。

画面不必完全像 Overcooked 那样从天空向下看。

可以使用类似二维插画场景的空间表达：

前景工作台 + 中景角色移动区域 + 后景柜子 / 冰箱 / 墙面设备。

角色在中间层移动。

当靠近某个工作站时，对应设备产生非常轻微的视觉提示。

例如：

靠近冰箱 → 冰箱把手出现轻微强调。

靠近砧板 → 可以放下手里的食材。

靠近炉灶 → 可以开始锅具操作。

不要让屏幕出现大量：

“PRESS E”

“INTERACT”

“OPEN”

之类文字。

优先使用自然的视觉反馈。

---

# 04. 移动与精细操作必须是两种不同状态

自由移动时：

玩家负责：

- 走动；
- 找东西；
- 拿东西；
- 放东西；
- 决定下一步去哪。

进入工作站之后：

镜头自然靠近。

此时暂时进入精细操作。

例如：

玩家来到砧板。

放下番茄。

点击 / 使用砧板。

镜头靠近。

番茄变大。

刀进入操作区域。

玩家开始真实切割。

完成之后退出近景。

玩家重新回到厨房空间。

这样同时解决两个问题：

**厨房足够大，可以探索。**

以及：

**食材足够大，可以精细操作。**

不要为了同时显示整个厨房，把切菜缩成屏幕角落里的小动画。

---

# 05. Venba 是食材交互和烹饪近景的重要参考

食材操作部分重点参考 Venba。

参考的是：

- 食材在二维画面中仍然非常有存在感；
- 烹饪器具占据明显画面面积；
- 玩家能够清楚理解自己正在碰什么；
- 每一个烹饪步骤都有具体视觉反馈；
- 动作简单但不廉价；
- 食材经过处理之后，画面真的发生变化；
- 2D 食物仍然可以表现出温度、湿度、熟度和质感；
- 做饭本身是一种令人愿意观看的过程。

但是本项目需要比 Venba 更自由。

Venba 更多用于指导：

**视觉表现、近景构图、食材存在感和操作节奏。**

本项目还需要加入更高自由度的物理规则。

---

# 06. “二维画面”绝对不等于“假物理”

这是整个项目最重要的原则之一。

本游戏需要做到：

**视觉抽象，行为真实。**

例如一个番茄可以是：

柔和的红色色块 + 简单轮廓 + 少量手绘纹理。

不需要变成照片。

但是：

刀切在哪里，

番茄就应该从哪里分开。

切成四块，

锅里就是四块。

炒软以后，

这四块仍然存在，只是形状、颜色和状态发生变化。

装盘的时候，

仍然应该认得出这些是刚才那四块。

---

# 07. 不允许使用“成品图片替换”伪装料理结果

这一条是硬性要求。

禁止：

玩家做完一道菜 →

系统读取菜谱名称 →

删除玩家实际做出的食物 →

替换为预先绘制好的“完成菜品.png”。

这种方式不符合本项目。

最终菜品必须由玩家实际使用的：

- 食材；
- 切割形状；
- 数量；
- 熟度；
- 酱汁；
- 调味；
- 混合；
- 摆盘；

共同构成。

如果玩家做的是：

三块煎肉 + 两块番茄 + 黄色酱汁 + 一条番茄酱线，

最后的盘子就应该真的包含这些东西。

---

# 08. 食材必须具有自己的行为规则

不要建立一个统一的：

FoodObject

然后所有食物只换图片。

至少需要通过数据驱动区分不同材料性质。

每种食材需要根据实际需要记录类似：

- 类型；
- 初始形状；
- 当前形状；
- 质量 / 数量；
- 可切割性；
- 软硬程度；
- 含水程度；
- 是否能够流动；
- 是否容易破碎；
- 当前温度；
- 熟度；
- 表面焦化程度；
- 内部状态；
- 当前附着酱汁；
- 当前调味；
- 当前容器；
- 当前切块关系。

不是所有字段都必须做成复杂科学模拟。

但是最终行为必须与现实直觉一致。

---

# 09. 不同食材必须真的不同

例如：

## 肉类

肉可以：

- 被切开；
- 产生不同大小的肉块；
- 加热后颜色变化；
- 表面逐渐产生焦化；
- 内部状态与表面不同；
- 小块通常比大块更快受热；
- 酱汁能够附着在表面。

玩家先煎再切时：

切开的内部不应该与外层完全一样。

---

## 番茄

番茄：

- 比肉更软；
- 切开后出现内部切面；
- 加热后逐渐软化；
- 长时间加热后结构进一步破坏；
- 可以释放一定水分。

不要把番茄和土豆使用完全相同的切割与受热表现。

---

## 叶菜

叶菜：

- 轻；
- 薄；
- 容易移动；
- 加热后萎缩；
- 颜色和形态发生变化。

---

## 块茎

例如土豆等：

- 比番茄坚实；
- 切块后形状保持更明显；
- 不同大小影响加工速度；
- 不应该像液体一样随便变形。

---

## 酱汁

酱汁：

- 有量；
- 有流动性；
- 有颜色；
- 有黏度；
- 能附着；
- 能混合；
- 可以留在容器、勺子和食材表面。

不要只把酱汁作为一个透明贴图覆盖在盘子上。

---

# 10. 勺子和铲子绝对不能只是两张不同图片

工具行为必须根据：

- 工具形状；
- 材质；
- 接触区域；
- 运动方向；
- 运动速度；
- 当前接触对象；

产生差异。

### 勺子

勺子有凹面。

因此可以：

进入液体 →

盛起一部分 →

离开锅 →

勺内仍然存在液体 →

倾斜 →

液体逐渐流出。

倒完以后可以存在少量表面残留。

---

### 铲子

铲子更适合：

- 推动；
- 刮动；
- 托起；
- 翻面；
- 聚拢固体食材。

不要让铲子拥有和深勺完全相同的液体容量。

---

# 11. 声音必须跟随真实接触

不要播放统一的“做饭声音”。

声音需要来自实际事件。

例如：

木勺 + 金属锅

与

金属铲 + 金属锅

应该明显不同。

同一把铲子：

轻轻碰锅沿

与

快速刮过锅底

也应该不同。

需要根据：

- 工具材质；
- 锅具材质；
- 接触位置；
- 接触速度；
- 接触力度；
- 当前食物；
- 当前液体量；

决定音效。

如果工具根本没有碰到锅：

不能播放刮锅声。

---

# 12. 挤番茄酱必须是连续操作

不要：

点击番茄酱 →

盘子突然出现红线。

正确流程：

玩家拿起瓶子。

移动到目标位置。

按住对应操作键 / 鼠标。

瓶身被抓握的位置发生局部压缩。

压力增加。

番茄酱从真实瓶口开始流出。

玩家移动瓶子。

酱汁形成连续轨迹。

移动慢：

单位距离酱汁更多。

移动快：

轨迹更细。

停在原地：

局部逐渐堆积。

松开：

瓶身回弹。

主要出酱停止。

瓶内剩余量减少。

---

# 13. 酱汁混合不能只是颜色替换

例如：

黄色酱汁与红色酱汁刚刚接触时，

首先应该能看见两个区域。

玩家开始搅拌以后：

出现局部拖曳 →

条纹 →

颜色逐渐融合。

混合程度由实际搅拌过程决定。

最终颜色根据：

- 两种材料；
- 实际比例；
- 透明度；
- 黏度；
- 混合程度；

决定。

不要求进行科研级流体计算。

但是需要在二维风格中提供符合现实直觉的近似。

不要简单：

red + yellow = 固定 orange sprite。

---

# 14. 真实感来自行为，不来自写实贴图

整个项目必须一直遵守：

**Good Pizza, Great Pizza / Venba 式二维美术语言 + 更高的行为仿真。**

不要为了实现：

肉熟了，

突然换成一张写实牛排照片。

不要为了实现：

酱汁，

突然加入照片级液体。

不要为了实现：

厨房，

突然出现 3D 模型。

所有内容继续使用：

- 几何化形状；
- 柔和轮廓；
- 少量手绘不规则；
- 统一色板；
- 简洁阴影；
- 必要的材质细节。

真实感通过：

运动、形变、接触、声音、连续状态和结果产生。

---

# 15. 顾客部分以 Good Pizza, Great Pizza 为重要参考

顾客来到柜台以后，

玩家首先看见的是一个人。

不要首先出现巨大的订单 UI。

顾客可以：

说今天发生的事 →

再自然提出自己想吃什么。

例如：

“今天那个方案又被退回来了。”

“改了五次。”

“最后他说还是第一版最好。”

“给我来点热的吧。”

“还有，别放葱。”

这些内容需要自然地属于同一段聊天。

---

# 16. 顾客不是订单机器

每位主要顾客需要具有：

- 性格；
- 说话方式；
- 当前心情；
- 基础口味；
- 明确忌口；
- 与玩家的熟悉程度；
- 最近发生的事情；
- 已经讲过的重要信息；
- 之前吃过什么；
- 对玩家某些自创菜的记忆。

同一个顾客下一次回来时，可以继续上一次的话题。

例如：

第一次：

“今天跟老板吵了一架。”

几天以后：

“你还记得上次那个老板吗？他今天居然跟我道歉了。”

这样玩家会逐渐觉得：

**这些人真的生活在这个小镇。**

---

# 17. 顾客反馈必须读取实际菜品

上菜之后不要只判断：

RecipeSuccess = true

然后播放“很好吃”。

反馈至少需要考虑：

- 有没有满足明确要求；
- 有没有放忌口；
- 食材组成；
- 熟度；
- 是否焦掉；
- 酱汁；
- 调味；
- 摆盘；
- 是否使用奇异材料；
- 顾客个人喜好；
- 当前心情；
- 与玩家关系。

例如：

顾客要求不要葱。

玩家真的没有
