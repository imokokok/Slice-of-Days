# 原型设计决策

## 范围依据

直接需求：Godot 开发、可接入大游戏、正常与怪异食材尽量多、物理属性、最终改为正面工作台式 2D、可实时看到试玩画面。最新视觉方向为日间暖色厨房，保持简化硬边几何；菜谱和海报从空白纸开始，自由组合食材、文字与照片。

截图仅为设计参考。采纳主线：经营已有 NPC 饭店的一个班次、30% 营业分成、自由搭配和烹饪、客人偏好、空白公共菜谱、菜名/照片/署名、自制海报受日程约束。保留可拓展性：主游戏日程、钱包、共享存档与社交。

没有把讨论中的每个提议视为已经确认的开发指令：全自由绘制食材、改做奶茶专店、排行榜、永居投票、昆虫榨汁等没有放进当前核心循环。

## 为什么不穷举菜谱

88 种材料、每锅 6 份会产生大量组合。使用材料标签、状态与 NPC 偏好直接评价任意组合；没有固定菜名才能得分的限制。重复材料不重复叠加喜好收益，避免刷分。普通顾客、老饕与猎奇顾客对怪异度使用不同权重。

根据后续试玩反馈，常用材料分区陈列在冷藏柜、常温架与奇异材料架，其余通过食材柜选择；开场演示直接显示客人和要求。番茄酱需挤压，酱瓶不参与料理。刀具采用按住拖动、松手放下；刀刃实际扫过食材后生成两个独立凸多边形刚体，每块可再切一次，总质量保持不变。松手后刀不再跟随鼠标，也不能继续切割。

## 物理和逻辑的交界

刚体负责位置、拖拽、重力、碰撞、质量、弹性和摩擦。锅的检测区把食材登记进纯数据料理。离锅时删除登记、保留食材之前的火候。锅内才继续受热。供主游戏保存的数据不含 Godot 节点或物理对象 ID。

## 自由拼贴与料理记录

完成料理后打开菜谱工作台，首先看到空白纸面。玩家自行把本菜使用过的食材图形加入纸面，也可以添加文字、导入照片、拍摄料理照片或使用装饰贴纸与画笔。保存用的菜名、署名和做法位于纸外；只有点击加入纸面的操作才会产生对应文字图层。

图层支持选择和拖移、旋转、缩放、复制、删除与前后顺序调整。食材图形和照片可用点选轮廓进行多边形裁剪；纸面坐标归一化，作品在不同大小的预览中保持相对布局。裁剪只改变该图层的可见形状，原照片保存在作品数据里。纸面编辑只修改作品布局，顾客评价仍使用真实料理的食材与加工状态。

布局保存在菜谱记录的 `poster` 字段中，包含图层、笔画、变换和裁剪轮廓；照片以 PNG base64 内嵌。选择保存后，重新打开菜谱或将 JSON 导入另一份存档，可以重建这张作品。独立宣传海报使用同一个画布组件，发布后再把宣传标签交给顾客日程规则。

“公共菜谱”当前指本地作品留存与手动 JSON 交换，没有云端账号、自动同步或实时共同编辑。后续主游戏可以通过现有发布事件和存储边界接入自己的共享服务。

## 后续优先级

1. 和主项目确认引擎版本、存档契约、退出键与场景路由，完成真实场景接入。
2. 用真人试玩调拖拽、接物、火候与顾客等待时间。
3. 按日间硬边暖色方向完善食材、工作台与音效，保持物体边界和操作反馈清晰。
4. 验收自由拼贴的空白初始状态、图层操作、照片裁剪和 JSON 往返恢复；由主游戏确定共享存储方案，需要联网时再接入身份、服务端校验与冲突处理。
5. 扩充烹饪器具、实体摆盘、份量和液体表现；保留纸面拼贴与真实料理数据的清晰边界。
