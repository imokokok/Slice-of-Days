# 写信、收信与回信：Kind Words / Paper Sky 参考拆解

核验日期：2026-09-26。本文区分**官方可核实事实**、**画面观察**、**本项目设计决定**和**尚待验收**。依据不只包括用户视频，还包括开发者 FAQ、历年更新和美术作者作品集。没有在本机通关或完整试玩两款商业游戏，不能将这次资料研究描述为“已亲自走完全部游戏”。

## 1. 从完整循环倒推体验

Kind Words 的主要交流不是聊天窗口中的连续即时消息，而是“提出近况 → 阅读陌生人的文字 → 写一封有对象的回应 → 收下回应 → 表达感谢 → 以后再回来”。这能给本项目的书桌、文字和寄出动作一个共同的中心：玩家在认真对一个人说话。

| 环节 | 核实到的机制 | 对本项目的设计意义 |
| --- | --- | --- |
| 发起 | 匿名发布简短求助，别人可写安慰、理解或温和建议。 | 自由信先问“今天有什么想说的”；不要默认打开巨大素材商城。 |
| 回应 | 阅读请求后给对方写信。 | 写回信时保留原信入口，避免回到空白桌面便忘记对方说了什么。 |
| 感谢 | 可以随信附贴纸，也能用贴纸感谢收到的信；获得的贴纸可重复赠送。 | 收到信的回馈应轻巧，装饰物可承载心意，不靠消耗稀有货币制造压力。 |
| 再访 | 信件和装饰形成可再次回看的个人积累。 | 使用可翻看的收信盘；完成一次寄送后回到安静桌边。 |

前三项来自 [Kind Words 官方介绍](https://popcannibal.com/kindwords/)。最后一项是结合其贴纸收藏与官方收件箱功能得出的体验归纳，不是“通关奖励”。

还有几项容易被表面美术掩盖的明确规则：公共请求优先照顾回复较少、等待较久的信；已回应的请求会过滤。来信可长期保留，但作品刻意限制陌生人持续私聊。感谢也不对应到某封具体回复，目的是减少表现评分的焦虑；纸飞机飞出屏幕后仍能再看到。这些是 [开发者 FAQ](https://www.popcannibal.com/wp/?p=423) 给出的规则，不是我们对源码的猜测。

官方后续打磨同样值得参考：收件箱可按新回复或原请求整理，未打开的信优先；进入输入区自动聚焦；Esc 不再擦除输入；允许删除不愿保留的回复。开发者也明确回避在线人数、赛事和数字滚动提示。[Kind Words 2020–2021 官方更新](https://store.steampowered.com/news/posts/?appids=1070710&enddate=1639749562&feed=steam_community_announcements)

**本项目自己的循环**：

```text
打开书桌
 ├─ 来访者对话 → 可选追问 → 收下照片/要求 → 回到 A4 信纸
 ├─ 自由写信 → 直接在 A4 上输入
 └─ 收信盘 → 阅读原信 → 回到 A4 回复
        ↓
正文 → 可选拼贴/涂鸦/水彩 → 检查成信
        ├─ 委托：折信 → 连续插入信封 → 拉下翻盖 → 封蜡 → 投入信箱
        └─ 漂流：卷纸 → 拔塞 → 对准瓶口逐渐插入 → 塞好 → 放入海面
        ↓
服务器确认 / 本地结果保存 → 温和完成反馈 → 继续阅读或回到桌边
```

这张流程图是本项目的设计与验收地图；每个步骤是否通过，以同批次验证报告为准。特别是“卷纸、拔塞、装瓶”是用户指定的原创转译，不能说成 Paper Sky 已有的瓶子玩法。

## 2. Paper Sky：不要把旧视频当成当前输入规则

[Paper Sky 官方商店](https://store.steampowered.com/app/1617230/Paper_Sky/) 的核心是纸飞机探索和阅读玩家留言，包含纸的形态变化；它不是与 Kind Words 相同的收件箱产品。

版本变化必须写清楚：2025-11-10 发布的 **October Update** 明确表示取消自由文字输入，改造留言体系。随后开发日志把词语与纸飞机加成、检查点联系起来；更新还提到将留言随游戏文件保留以支持离线阅读。它说明“纸张寄托某人的话”可以成为世界的一部分，却不能证明当前版本仍使用旧视频里的自由输入。[Paper Sky 开发者更新：October Update / January Update / December Update](https://steamcommunity.com/app/1617230/allnews/)

我们的取舍是保留用户要求的自由写信，不移植词语升级、点赞积分或飞行挑战。可借鉴的体验是：文字先留在纸上，寄出有一段可感知的动作，动作完成后给玩家一点安静的停留。平面桌面与海面即可承载这个过程。

## 3. 打字：外观、输入能力、逐字演出分开实现

用户提供的 Kind Words 片段中，可观察到浅色纸面、深色正文、当前输入位置，编辑框的系统边框很弱。它支持“文字直接落在纸上”的视觉判断；片段和官方资料都不能确认它用了哪一种 Unity 输入组件、内部排版算法、中文输入法实现或每次按键音的触发代码。这里没有宣称逆向得到了商业游戏源码。

本项目的输入实现采用 Godot 自身的 `TextEdit`。官方 API 提供光标、选区、换行、撤销/重做、粘贴和 IME 相关能力；这些能力应保留，去掉的只是编辑器式外框。[Godot TextEdit 官方文档](https://docs.godotengine.org/en/stable/classes/class_textedit.html)

| 场景 | 应有行为 | 验收重点 |
| --- | --- | --- |
| 玩家写正文 | 真实输入直接显示；中文候选仍由输入法管理。 | 中英文、标点、换行、选区替换、撤销；候选未提交时不重复写入。 |
| 来访者说话 | 逐字显示，点击可补全本句，再点前进；玩家追问后回到主线。 | 不能因快速双击漏句，历史仅记录已发生内容。 |
| 写字声音 | 只为实际提交的输入提供短反馈，连续键入不过度叠加。 | 中文拼音候选阶段不为每个底层键伪造一份最终字音；删除、翻页、纸张和工具声音有区别。 |
| 退出/切工具 | 正文和编辑位置尽可能保留。 | 关闭收信盘或暂离不清空草稿；进入下一封才创建新正文。 |
| 成信预览 | 文本、涂色、纸片成为同一张 A4 输出。 | 中英长文不能静默裁掉；绘制和最终导出尺寸一致。 |

这一表是我们的技术方案与验收标准，并非两款游戏的内部实现说明。打字时添加人工逐字延迟会妨碍编辑，因此玩家输入和 NPC 逐字演出不能共用同一套延迟队列。

## 4. 非 3D 美术与书桌的融合方法

Kind Words 美术作者 [Luigi Guatieri 的项目页](https://luigiguatieri.com/projects/7201250) 展示了 UI 概念、标题与贴纸设计，是可追溯的视觉参考；该页面是作品展示，未给予游戏内使用这些图像的许可。结合用户视频，本项目采用下面的原创方案：

| 层次 | 本项目的处理 | 要避免的结果 |
| --- | --- | --- |
| 空间 | 暖木书桌，后方街道与海的小窗、可拉百叶窗；保持固定 2D 视角。 | 摄像机绕转、连续镜头漂移，以及把整张参考图作为不可操作背景。 |
| 纸 | 单页 A4 是视觉中心；纸纹、轻微翘边、薄阴影体现厚度。 | 绿边框、装订孔、大装饰框把信重新变成手账本。 |
| 工具 | 笔、工具卷、信盘、素材册作为独立入口；需要时才展开。 | 桌面常驻多排矩形按钮。 |
| 对话 | 明确说话者、正文、玩家应答和少量追问；附件到被提及时再出现。 | 把来访者说话画成又一张大邮票边框，叠住工作纸。 |
| 排版 | 正文优先，空白有节奏，弱化操作说明的抢眼程度。 | 用大量装饰字体替代可读正文；每个区域颜色都同样鲜艳。 |
| 动作 | 拿起时轻微抬高、放下有纸感、抽屉有惯性、遮挡连续。 | 物件跳层、塞入瞬间消失、蜡印与信封分离。 |
| 听觉 | 低音量且可静音的真实纸张/摩擦/按键/工具录音。 | 把所有行为绑定同一段 UI 点击声。 |

这里的暖木、奶油白、灰蓝和橄榄色还遵循用户的 Solmere 街景参考；并非声称这些色号逐一取自 Kind Words。贴纸轮廓、角色、商标和原作房间均不移植。

## 5. 温暖感要落实到动作和失败处理

以下都是本项目设计决定：

1. **先有人，再有材料。** 对话中先听见来意，接着才拿到照片和约定；素材标题要能对应对话里的地点与记忆。
2. **允许只写一封普通的信。** 纯正文就能完成；拼贴、水彩和装饰是表达方式，不能成为每封信的强制门槛。
3. **不给关心打分。** 漂流信界面不放受欢迎度榜、倒计时或连续签到催促；列表只提供读信所需信息。
4. **保留用户已确定的互惠规则。** 自由寄出后，需要回复一封信才能再次自由发信。用“给另一封来信留一句回音”解释下一步；允许暂离，草稿保留。它是本项目规则，不能包装成 Kind Words 的原规则。
5. **保留旧信可回复。** 不照搬 Kind Words 的对话限制；旧信有原文入口和回复关系。不要擅自新增联系方式交换或私聊系统。
6. **寄出前物件一直可见。** 纸卷穿过瓶口时分层裁切；瓶塞必须先取下，再放回；整瓶移动时纸卷和塞子跟随瓶身。
7. **失败仍然是一封在手里的信。** 网络拒绝或断开不播放寄送成功，也不销毁草稿。可重试的寄送沿用同一请求编号，避免收到两份。
8. **成功需要可核验的终点。** 服务端确认后再显示完成；已确认结果先持久化，再播放离开动画，避免动画中关窗导致重复发送。

## 7. 与当前代码的映射、交付边界

| 体验 | 代码入口 | 必须实际验证的结果 |
| --- | --- | --- |
| A4 上直接写正文 | `scripts/main.gd` 的 `letter_text`、`LetterWriting` 与导出流程 | 原生键盘/中文输入法实测、关闭重开和成信导出。 |
| 来访者对话、追问、回看 | `commission_dialog.gd`、`commission_history.gd` | 逐句推进、附件时机、恢复、双语与不同尺寸无覆盖。 |
| 收信、旧信及回信 | `bottle_dock.gd`、`bottle_client.gd` | 两个独立身份能收发；原文可读；回复义务只由真实寄送改变。 |
| 卷纸与瓶塞仪式 | `bottle_finishing.gd` | 拖动顺序、连续遮挡、存档恢复、失败可重试。 |
| 桌面与百叶窗 | `office_scene.gd`、`desk_drawers.gd` | 窗帘拉动有效、值能保存、场景入口与抽屉不相互遮挡。 |

代码中已有入口不等于全部已通过验证。特别是原游戏完整试玩、公共服务器上线、跨公网玩家运行和原生中文 IME，均不能由源码阅读或 GPU 截图推断为完成；最终结论应附本次真实测试结果。Kind Words 式“贴纸致谢/赠送收藏”在这里属于研究发现，本表没有宣称已经建立了对应联网功能。
